# 时间同步方案总结

本文汇总当前项目中 STM32 时间同步的完整设计：单一时钟域、硬件输入捕获、GPS 时间锚定与换算、中断/缓冲/丢帧机制、实时组合的延迟特性，以及已知局限。代码引用均以 `firmware/Src/main.c` 为准。

## 1. 设计目标与总体骨架

| 要点 | 内容 |
|---|---|
| 目标 | 把 MPU6050 的 100 Hz IMU 样本和 ZED-F9P 的 1 Hz GNSS 观测标记到统一的 GPS 时间（周/周内微秒），供组合导航（松/紧耦合）使用 |
| 核心思想 | **单一时钟域 + 硬件输入捕获**——所有事件在同一个时间基准下被"定格"，不让软件延迟混入 |
| 物理连线 | F9P 1PPS → PA0/TIM2_CH1；MPU6050 DATA_RDY → PA1/TIM2_CH2 |
| 分工原则 | 中断只"搬运"（搬寄存器值），主循环做 I2C、UBX 解析、串口输出 |

贯穿全程的一句话：**"硬件先记账、软件后取走"**——硬件在边沿到来时先锁存计数值，避免把 ISR 响应延迟直接混入时间戳；软件随后取走并换算成 GPS 时间。捕获寄存器和溢出标志的深度仍然有限，CPU 长时间不能处理中断时仍可能发生覆盖或漏计。

## 2. 单一时钟域（TIM2 时间基准）

- TIM2 自由运行计数器：72 MHz 时钟分频到 **1 MHz（1 µs 分辨率）**，16 位 CNT（ARR=0xFFFF，每 65.536 ms 溢出一次）。
- 溢出由 UIF 中断累加，把时间轴扩展为 **48 位**（高 32 位溢出计数 + 低 16 位 CNT），按微秒计数约 **8.92 年**回绕一次。
- 代码：TIM2 初始化 `main.c:393-411`；`timer_now_unlocked` / `timer_capture_time` 处理"读低字前刚溢出"的竞争（UIF pending 且捕获值 < 0x8000 时高字 +1），`main.c:209-242`。

### 半周期消歧的前提与边界

`timer_capture_time` 里 `if ((status & TIM_UIF) && capture < 0x8000u) ++high` 属于典型的**半周期消歧**：用捕获值落在 CNT 的高半区还是低半区来判断该边沿发生在回卷前还是回卷后。它隐含一个前提——**从 capture 发生到软件完成判定的最大延迟，小于 TIM2 半个回卷周期**。

本项目参数下回卷周期 `T_wrap = 65536 µs = 65.536 ms`，半周期 `T_half = 32.768 ms`。在当前 100 Hz IMU 采集、72 MHz MCU 和正常中断负载条件下，capture 到软件判定的延迟预计远小于 32.768 ms；结合实测约 10 ms 的稳定捕获间隔，该半周期消歧假设在正常工作状态下成立。只有当 CPU 被阻塞超过约 32.8 ms、且捕获值恰好落在低半区时，才会出现 epoch 歧义——但这种负载程度下通常已同时出现 `CC2OF`、`g_debug_interrupt_overruns`、20/30 ms 甚至更大的 `dt`、以及 I2C/UART backlog，属于更上层的架构问题，不需要在时间戳消歧这里单独解决。

### ISR 内的完整处理链（第一阶段加固后）

```text
DATA_RDY / PPS 边沿 → TIM2 硬件捕获 → CCxIF + CCRx
→ SR 快照
→ 立即 acknowledge 快照中的 UIF / CCxOF
→ 记录 CC2OF（observed overcapture，非丢样计数）
→ 读 CCRx 清 CCxIF
→ 补读一次 UIF（补偿 snapshot→CCR 之间的 timer wrap）
→ 半周期判别构造 48-bit 时间戳
→ 主循环消费
```

诊断量语义（第一阶段后已收敛）：

| 指标 | 准确含义 |
|---|---|
| `g_debug_interrupt_count` | ISR 实际观察并处理的 CC2 capture 次数（非物理边沿总数） |
| `g_debug_interrupt_overruns` | 单槽软件 mailbox 尚未消费时又来了新的 capture（软件级覆盖） |
| `g_debug_cc2_overcapture` | 软件观察到 `CC2OF` 的次数，不等于丢失 epoch 数（硬件级覆盖） |
| `g_data_ready_us` / `dt` | 最终保留下来的真实硬件 capture 时间轴 |
| `g_debug_i2c_errors` | capture 后读取 MPU 数据失败 |

## 3. 硬件输入捕获（核心机制）

- **定义**：定时器硬件在引脚边沿（本项目为上升沿）到来的**同一时钟节拍**，自动把 CNT 计数值锁存进捕获寄存器（CCR1/CCR2），并置 CCIF 标志——整个过程不需要 CPU 执行指令。
- **捕获的"事件"**：PPS 上升沿（CH1）、DATA_RDY 上升沿（CH2）。
- **捕获的"值"**：CNT 计数器读数 = 边沿瞬间的本地微秒时间（**相对时间**，不是 GPS 时间）。
- **与软件打时间戳的本质区别**：软件方式在中断里读 CNT，读到的 = 事件时刻 + 随机中断延迟；硬件输入捕获先锁存边沿时刻，因此在**下一次同通道捕获尚未覆盖 CCR**的前提下，ISR 晚一些读取不会把这段延迟加入时间戳。若新边沿先到，会产生 `CC1OF/CC2OF` overcapture，旧捕获值可能丢失。
- **项目里有两处"硬件记账"**：CC1/CC2 输入捕获（锁存边沿时刻）+ UIF 溢出标志（扩展时间轴）。
- 代码：`TIM2_IRQHandler` `main.c:244-266`。

## 4. GPS 时间锚定（TIM-TP + 1PPS 双通道）

- F9P TIMEPULSE 配置：**GPS 时栅格、1 Hz、100 ms 高电平、对齐整秒 TOW**。
- **UBX-TIM-TP 消息**（0x0D 0x01）给出**下一个** TIMEPULSE 的 towMs/week/flags/refInfo。`flags.bit0=0` 表示采用 GNSS 时间基准，并不是“时间有效”标志；`refInfo.reference=0` 表示 GPS 时基准。当前固件检查 GNSS 时间基准、GPS reference 和 `week≠0` 后存入 `g_next_gps_week / g_next_gps_tow_ms`，但尚未检查 `flags.bit5`（`TpNotLocked`）和 `flags.bit4`（`qErrInvalid`），见 `main.c:759-770`。
- 该值**不被立即使用**，而是等**下一个 PPS 上升沿**由硬件捕获时快照进 `g_pps_*`，且 `g_next_gps_time_valid` 一次性清零（`main.c:253-256`）——保证"这个周/毫秒"确实对应"这个脉冲"。
- 为什么不等消息的软件到达时刻：串口传输/解析延迟不定；脉冲边沿是硬件精确时刻。
- 结果：在当前有效性判据通过时，**本地计数器时刻 ↔ GPS 周内整毫秒** 在脉冲边沿上建立锚点；锚点是否真正锁定、绝对精度是否达标仍取决于 TIM-TP 状态检查和实际测量。

## 5. 时间换算：gps_time_from_local

```text
tow_us = pps_tow_ms × 1000 + (local_us − pps_capture_us)
```

- 前进方向超过 604800 s → `++week`；回绕方向（local 早于 pps）→ `--week` 并跨周修正。
- 无有效锚点 → 返回 `time_valid=0`，week/tow 清零。
- **IMU 样本的 `local_us` = DATA_RDY 硬件捕获时刻**（`main.c:1362` `now = g_data_ready_us`），不是软件读取时刻——所以每个 100 Hz 样本被精确放到 GPS 时间轴上。
- 代码：`gps_time_from_local` `main.c:1062-1103`；IMU 输出 `print_sample` `main.c:1105-1130`。

## 6. ISR 与中断响应延迟

- **ISR（中断服务程序）**：硬件事件触发 CPU 跳去执行的函数，本项目如 `TIM2_IRQHandler`。
- **响应延迟**：事件发生 → ISR 第一条指令执行之间的时间。来源：CPU 正在跑其他代码、完成当前指令、压栈保存现场、取向量跳转、`cpsid i` 临界区、更高优先级中断占先。
- 延迟不可避免且**抖动**（每次不一样）。
- **正常负载下为什么显著减小影响**：时间戳先由硬件锁存，ISR 只是取结果。只要下一次同通道捕获和多次定时器溢出尚未覆盖当前事件，响应延迟主要影响“什么时候读到”，不会直接改变已锁存的 CCR 值。
- 工程要求：ISR 尽量短（只搬寄存器、清标志就返回），把 CPU 留给主循环。

## 7. 丢帧与缓冲机制（CPU 忙/中断期间数据去哪了）

| 数据路径 | 缓冲 | 会丢吗 | 防护/计数 |
|---|---|---|---|
| F9P 串口字节（USART2） | 硬件仅 1 字节 DR | 不读会被新字节**覆盖** | ISR 立即搬进**环形缓冲**（`main.c:287-295`）；缓冲满 → `g_debug_gnss_rx_overruns` |
| IMU 数据（I2C） | 输出寄存器保留最新帧 | 晚读会读到最新帧，但此前样本可能被覆盖而**跳帧** | `g_debug_interrupt_overruns` 只统计软件待处理标志已置位的情况（`main.c:260`） |
| 时间戳（CCR） | 每通道一个捕获寄存器 | 下次同通道边沿可覆盖旧值并置 `CC1OF/CC2OF` | 当前 ISR 尚未单独统计硬件 overcapture |

- 核心认知：短暂中断延迟通常由外设寄存器或软件缓冲吸收，但这些缓冲都有上限；超过容量后旧数据仍会丢失。
- USART 环形缓冲和软件待处理 IMU 目前已有部分 overrun 计数；TIM2 的 `CC1OF/CC2OF` 以及极端情况下的多次 UIF 溢出尚未完整观测，见 `docs/KNOWN_ISSUES.md`。

## 8. 实时组合与延迟

- **两个概念必须分清**：延迟 = 数据多晚到（影响"输出多新鲜"）；时间戳 = 数据在时间轴上的位置（决定"算在哪一刻"）。**延迟 ≠ 时间误差**。
- 实时组合需要可靠的测量历元时间；本方案提供 1 µs 计数分辨率，端到端延迟只要有限且不持续堆积，就可以按测量时间递推，而不是把数据到达时刻当作测量时刻。1 µs 分辨率不等同于已经验证的 1 µs 绝对同步精度。
- 端到端延迟流水线（量级估算，以实测为准）：

```text
DATA_RDY 边沿 → CCR 锁存：硬件完成（受定时器输入同步与 1 µs 量化约束）
→ ISR 搬变量：1–3 µs（不影响时间戳）
→ 主循环取走 + I2C 读 14 字节：几十 µs–1 ms（I2C ≈ 350 µs）
→ 串口输出 ~100 字符 @460800：≈ 2.2 ms
→ USB + 上位机解析：1–10 ms（tty 缓冲 + 调度）
→ 组合解算可用：合计 ≈ 3–15 ms
```

- 需要重点控制的是时间戳错误、延迟抖动、乱序和持续积压。当前松组合支持对缓存范围内的**延迟 GNSS**回退更新并重放 IMU；重复或乱序 GNSS 历元会被拒绝，并未进行通用的乱序重排。
- **真正破坏实时组合的典型问题**包括：① PPS 未锁定或断线后继续使用旧锚点；② 持续丢 IMU 帧；③ 捕获/串口缓冲覆盖；④ 处理速度长期低于输入速度。
- 若需更低端到端延迟（闭环/实时反馈场景）：优化优先级为 上位机解析与调度 > 串口输出量（裁剪 IMU 行字段）> 波特率（已 460800）。这些优化只让数据"更早到"，不会让时间戳更准。

## 9. 各数据流的时间戳语义

| 数据 | 时间戳 | 来源/含义 |
|---|---|---|
| IMU | `gps_week / gps_tow_us / time_valid / timer_us` | PPS 锚点 + DATA_RDY 硬件捕获时刻外推（核心） |
| GNSS | `gps_week / gps_tow_ms` | NAV-PVT 自带 iTOW |
| GNSS | `rx_timer_us` | 完整 UBX 帧通过校验的 STM32 本地接收时刻（软件戳） |
| RAWX | `gps_week / rcv_tow_s` | RXM-RAWX 自带观测历元时间 |
| RAWX | `rx_timer_us` | 该帧到达 STM32 的时刻（传输延迟分析用） |
| `# sync` | 每个 PPS 一行 | pps 计数、捕获时刻、绑定的 week/tow/valid |

上位机（`tools/capture_serial.py`）保留 STM32 输出的 GPS 周、周内时间和本地计数等原始时间字段，同时负责协议解析、单位换算，并增加 `time_s`、`dt_s` 等派生列。时间锚定由 STM32 完成，上位机不会重新给 IMU 样本生成测量历元。

## 10. 精度与已知局限

- **分辨率**：PPS 与 DATA_RDY 使用同一个 1 MHz TIM2 时钟域和硬件输入捕获，计数分辨率为 1 µs，避免了普通 ISR 响应延迟直接进入时间戳。
- **实际同步精度**：还受 STM32 定时器时钟频偏、输入同步、线路延迟、F9P TIMEPULSE 锁定状态和接收机误差影响，不能仅由“F9P PPS 指标 + 1 µs计数”直接给出。当前固件也未使用 TIM-TP 的 `towSubMS`、`qErr` 做亚毫秒/误差修正，应通过示波器、逻辑分析仪或外部时间基准实测。
- **已知局限（`docs/KNOWN_ISSUES.md` P1）**：`time_valid` 既不检查 `TpNotLocked`，也不检查最近一次 PPS 的新鲜度。PA0/TIMEPULSE 在成功同步后断线时，固件可能继续从旧锚点外推并保持 `time_valid=1`。计划：补充 TIM-TP 锁定/误差位检查，超过约 1.5–2.5 s 无新 PPS 时标为无效，并输出 PPS 年龄/计数。在修复前，组合导航应同时检查 `# sync` 行的 PPS 计数是否持续更新。
